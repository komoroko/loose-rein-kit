# /tasks — reference

Read by `/tasks` at the step that names a section, not up front: what is here is needed at one
step, and the procedure itself stays short enough to survive a compaction of the session whole.

## Reconcile after a roll back
On a re-run after rolling back upstream with `/revise`, if `plan.yaml` already has tasks, **do not rebuild from scratch**. Reconcile the revised design against the existing tasks:
- The `/revise` step normally already marked the impact closure `needs-revision` in code (`rein revise --impacted T-00x,T-00y` — seeds plus transitive dependents). If it did not, mark it now (the read-only enumeration is `rein dag --impacted T-00x,T-00y`).
- Reclassify each marked task: **keep** (unaffected — restore its former status, stating why: `rein task reset T-NNN --status todo --reason "…"` for a task that was `todo`, `rein task keep T-NNN --reason "…"` for one that was `done`, which holds only while the task differs from what the mandate froze by paths added to an `artifact` criterion that `HEAD` has) / **modify** (needs fixing → stays `needs-revision`) / **obsolete** (no longer needed → mark in notes, do not delete) / **deferred** (moved to the next cycle → delete it from `plan.yaml`, then record it with `rein task defer T-NNN --reason "…"`, which moves its status aside and puts it on the acceptance screen; a status left for a task the plan no longer declares stops every graph reader) / **new** (added). "Keep" is a deliberate reclassification presented at the mandate gate, never a silent default.
- A task that was **`done` but invalidated** reverts to `todo` (needs reimplementation; `/revise`'s mark output lists former statuses). The implemented code stays on the branch but is back in scope plan-wise.
- After reconciling, re-run `rein dag --trace` and confirm the **task thread is reconnected to the revised requirements/design** (no new requirement left uncovered, no dangling reference to a deleted requirement) (confirm exit 0; 1=missing, 2=nothing to check).
- At the mandate gate, in addition to the usual plan, present the **impact (the impacted list and the keep/modify/obsolete/deferred/new classification)** and the **consistency trace** to get re-approval.

## Brownfield
if `docs/05-current-state.md` exists (an adopted repo), **read it first**. Cut tasks to **this cycle's remaining delta** — never create a task that re-implements a capability the baseline already lists as implemented. When the cycle completes an in-flight partial implementation, put an **absorb task** first (kind: foundation): write acceptance-level tests around the existing partial code and pin it green, so the remaining-work tasks stack on a verified base; reference the existing code in the ticket's "Notes / design decisions". **Never create a task as `done`** (a new task is always `todo`) — what already works is baseline description, not a task. If a delta requirement names the combined capability (existing part + remaining work), point the absorb task's `claim_ids` at that requirement's claim and the `rein dag --trace` coverage holds.

## Plan fields
**`scope` first, because it is what the human is actually delegating.** `plan.yaml`'s top-level `scope: {include: [...], exclude: [...]}` is the set of paths the loop may change for the whole cycle, and `rein guard` denies a write outside it once the mandate is approved. Each entry covers the path it names and everything beneath it. An empty `include` is unbounded — honest for a cycle that has not narrowed itself, and a thing to say out loud at the gate rather than to reach by omission. Per-task `scope` (below) sits *inside* it and is the loop's own division of labour.

The sub-issues are frozen with the plan, and changing one — adding, removing, or moving a criterion between them — **is** a gate move, `/revise --to mandate`: `acceptance` lives on each sub-issue, and a re-cut of them is a shape in which a criterion gets softened. What the loop settles alone is the order it consumes the DAG in and **how it groups an issue's sub-issues into launches** — no grouping moves a criterion off its sub-issue, so nothing approved changes. That is the reason to cut sub-issues fine and let the loop bundle them, rather than to cut coarse tasks you might later want to split. An edge the plan missed is added after the freeze with `rein task order`, beside the plan; a file a task's change necessarily drags along (a test pinning a constant it changes) is added with `rein task scope-add`, only inside the config's `guard.scope_additions`. Before freezing, grep for what each task changes — a constant, a model id, a message — and put every test that asserts it into that task's scope, so neither is needed; when the mandate is rolled back those edges come back here — `rein revise` lists them — to be written into `blocked_by` where they still hold. The plan's work is `issues:`, each `{id: I-NNN, title, kind (foundation|parallel|integration), blocked_by: [I-…], sub_issues: [...]}`. Schema per sub-issue (`plan.schema.json` is `additionalProperties: false`, so these are the only keys and a stray one fails the write): `id` (unique across the plan, `T-NNN`) / `title` / `blocked_by` (array of sub-issue IDs of the same issue, no cycles) / `claim_ids` (the claims this task answers — that, not a `req` string, is what `rein dag --trace` follows back to a requirement) / `domains` / `risk` / `scope` (where this task's work belongs — the loop checks the diff against it; each entry covers the path it names and everything beneath it, and the trailing `/` is optional) / `acceptance` (this task's own bar, below) / `operator_surface` (what this task will require of a *person*, and whether it can be undone, below) / `requires` and `produced_by` (what a person has to provide *before* the task can run, below). **Status is not a task field**: the live value lives in `.rein/state.yaml.tasks` (`todo | in-progress | blocked | needs-revision | awaiting-evidence | done`; newly created = `todo`) and `/build` writes it. There is likewise no per-task `test` command: the DoD is `quality_gate` in `config.yaml`, one definition for every task.

**`acceptance` is not a second quality gate.** The DoD says the code is *sound*; a task's acceptance criteria say it did *what it was for*, and both run. Each entry is `{id: A-1, statement: <one thing, stated so it could be false>, evidence: {...}}`. `evidence` is optional — most criteria are prose, and saying so is honest — and comes in three kinds: `command` (an argv run in a sandboxed profile, decided by exit status), `artifact` (the named paths must exist — and must lie inside the task's own `scope.include`, which plan validation enforces; a criterion that says a log, a screenshot or any other file exists declares it this way rather than in prose, so a file the task cannot write is refused here and not after it is built), and `external` (evidence this loop cannot obtain: a staging check, a device, a person). A task carrying an `external` criterion reaches **`awaiting-evidence`**, not `done`, until a human records the observation with `rein evidence record`. Putting these in the plan rather than the ticket keeps them out of the implementer's hands: a human freezes this list at the mandate gate. Any `evidence` may also carry **`produces`** (paths this task creates — a directory counts, which is how a package another task writes modules into is declared) and **`reads`** (paths it reads without producing: a fixture, another task's output). They are not prose: the plan is checked against them before it can freeze. Each produced path must lie inside the task's `scope`, no two tasks may produce the same path, a task that produces or reads anything under another task's path must depend on it (`blocked_by`, directly or through others), a produced path git ignores is refused (no worktree will ever have it), and a read path nothing produces must already be tracked. Declare them for every criterion that touches a file: a criterion naming no path contributes nothing to that check, and `rein approve mandate` lists each such criterion so the human can see where a contradiction could still hide. **A file the review cannot read as text** — a screenshot, a recording, a PDF, a dataset — leaves acceptance's coverage insufficient unless something reads it, and at high risk that blocks the gate. Where it sits never settles that. Either the kind is read by a file reader declared in `config.yaml` (`review_policy.file_readers`: a deterministic command in the quality-gate image that accounts for the whole file), or the criterion names the file's own path as an `artifact`. Raise it here, while the mandate can still be edited.

**`requires` and `produced_by` are what a person has to provide *before* the work can run** — the opposite direction from `operator_surface`, which is what the finished work will ask of somebody. Take them from the design's "What this requires of a person" lines. Each `requires` entry is `{says, probe | file}`: `says` is the line a person is shown, in their words ("a logged-in browser listening on port 9222", "the TTS model installed on this machine"); `probe` is an argv whose exit status says whether it holds (`["curl", "-sf", "http://127.0.0.1:9222/json/version"]`, `["python", "-c", "import torch"]`), or `file` is a path that has to exist. A probe runs where the implementer will — `executors.agent_profile`, or the host when agents run there — unless it names an `executor_profile` of its own; a probe that cannot be run at all stops the run as a machine fault rather than counting as unmet. `rein build` checks them before every launch: a task with an unmet one is not launched and spends no budget, and when nothing else can run the loop names **everything** the remaining plan still needs from a person in one list. `rein approve mandate` prints the same list the moment the plan freezes. When the deliverable itself can only come from a person — labels judged by eye, a recording, a measurement on a device — make it its own task with `produced_by: person` and an `artifact` criterion naming the file. No implementer is ever launched at it (an agent sent at a person's deliverable either stops or fabricates it); the loop waits for the file to be committed on the work branch, records which commit and author it came from, and the tasks that read it depend on it through ordinary `blocked_by`. A precondition left as prose is found by a paid launch, one at a time.

**`environment` is what a task's work needs from the machine, supplied by the loop rather than inherited.** `environment.env` sets variables for the implementer and for the task's `requires` probes (`$HOME`, `~`, `${NAME}` expand at launch on the loop's machine; a reference to an unset variable is an unmet precondition, and so is any reference at all when the implementer, an `operate` step or a probe runs contained, because a host path names nothing there — write a literal value). `environment.allow` lists the exact command prefixes that task's implementer may run without asking, granted for that launch only. Declare them here instead of editing the repository's standing `permissions.allow` or relying on the operator's shell: a rule added there for one host task stays for every later session, and a variable that lived only in one shell is gone the next time the loop is started from another.

**`operate` is the long, deterministic part of a task, run by the loop rather than by an agent.** A full measurement run, a generator that takes hours, a migration dry run: list each as `{name, command, executor_profile?, timeout_sec?}` and the loop runs them in the task's worktree and `environment`, after the implementer reports `implemented` and before the quality gate. They run the implementer's code, so they run where a quality-gate step does (`executors.quality_gate_profile`); a run that needs the network or data outside the worktree names a profile that grants it, and that choice is on the mandate screen. Put what the run writes inside the task's `scope`: the loop checks it after the run as it checks the implementer's change. The implementer writes the tooling and is told not to start it — a run begun inside an agent's turn dies when the turn ends, and waits out every session limit inside it. A step that ran and failed goes back to the implementer with its log; one the machine could not run stops the build as a machine fault.

**An irreversible task carries a `rehearsal` and an `attempts` budget, or the mandate does not open.** `rehearsal.tasks` names reversible tasks it waits for whose criteria run the same path on small real input (ten real records through every stage, a dry run against a copy) — the first contact with real inputs must not be the one that cannot be undone. `rehearsal.scale` is `{unit, rehearsal, run}`: what a failure strikes one at a time (model calls, records) and how many of them the rehearsal and the run each make. The mandate screen prints the smallest per-unit failure rate the rehearsal is likely to show; a few records ahead of several hundred calls shows none of the few-percent failures that stop a long run, so size it to the failures you need to see, or make it exercise them on purpose. When no smaller form exists, `rehearsal.waived` says why, in a person's words. `attempts` is `{max, cost}`: how many runs the approval covers and what one spends. For a task with `operate` a run is one start of those steps, and every start counts — a red step or a reviewer's finding after the run sends it round again, and that start is an attempt too; the loop does not start one past `max`. Without `operate` the loop never starts the run, so what it counts is implementation attempts and a run launched by hand is in no count: put the run in `operate` when its launches are what the budget prices. When one failure anywhere stops the whole run, put the arithmetic in `cost`: n checks each passing with probability p pass together with p^n, and a plan that needs 200 checks at 99% has a 13% run.

**`premises` are what the plan believes about the world and nobody has measured yet** — a CLI flag's behaviour, a service's error shape, a dataset's size. Neither a settled answer nor an `unknown`: write it down instead of writing criteria that silently depend on it. Each is `{id: P-N, says, probe, observed_by?, fallback?}`: `probe` is an argv the loop runs (exit 0 = the premise holds), `observed_by` the task whose work makes the probe meaningful (the one that installs the CLI or collects the fixture; omit it and the probe runs before anything else), and a criterion that rests on it says so with `assumes: [P-N]`. Such a criterion is provisional: its task does not run until the premise is observed. **State the `fallback` whenever you can**: `{says, criteria: [{task, id, statement, evidence?}]}` — the criteria that replace the ones resting on the premise if it turns out false ("if `--max-turns 1` does not yield `error_max_turns`, verify the TRUNCATED branch with a factory fake"). The human approves it with the mandate, so the loop can apply it with no roll back. A premise found false *without* a fallback parks only the tasks resting on it and asks a person about those.

**`operator_surface` is the Expected side of "what does this now require of somebody".** Each entry is `{kind, name, paths, reversible, adr?}`: `kind` is one of `persistence` / `public_interface` / `dependency` / `default_value` / `observability` / `security_boundary` (the same words the blind extractor uses, so the two sides compare directly); `name` is what a person deals with, in their words — a settings key, a table and column, a queue, an endpoint; `paths` is where that surface can be *read* at the end, which is both what an extracted statement's code anchor is matched against and what the acceptance gate offers as the as-built view; `reversible` is that line's answer, as a boolean, and it is required — there is no default, because silence must not read as "yes"; `adr` points at where the requirement and its reversibility were decided. Take these from the design's "What this requires of a person / reversibility" lines — do not invent them here. **`reversible: false` adds a gate.** That task becomes a contact point of its own: `rein build` stops in front of it and a human runs `rein approve T-NNN` before it runs, because afterwards there is nothing left to approve. So write `false` when undoing it means undoing something outside this repository — data migrated, a version published, a charge made — and `true` when reverting the commit is enough. Marking everything irreversible is the same failure as marking nothing: the first spends a human's attention on reverts that cost one task, the second runs the one thing they would have stopped. **Declaring nothing is allowed and is not a shortcut**: whatever the code turns out to require of somebody still reaches the acceptance gate, just as something nobody foresaw, at the top of the screen. Example entry: `{id: I-001, title: "the shared schema", kind: foundation, sub_issues: [{id: T-001, title: "define shared schema", claim_ids: [C-001], risk: low}, {id: T-002, title: "migrate the readers", blocked_by: [T-001], claim_ids: [C-001], risk: low}]}`. The ticket file `docs/tasks/T-NNN.md` is where the human-facing notes live, including which requirement it covers. This is the deterministic truth read by `/build` (the installed `rein build` orchestrator) and `/status` (`rein dag`, which joins `plan.yaml`'s structure with `state.yaml`'s status). fan-out, frontier, layers, and the critical path are derived from `blocked_by`, so they are not stored.

## Reviews before the mandate
Run **`rein reviews show --stage tasks`**: it says whether the adversarial review is on at `tasks` and lists each review added there, with the question it asks of the document. Switching any of them back on or adding one is the human's, never yours. **Adversarial review** (unless it is **OFF** — then skip it and say so when you present the gate; the approval screen names it too): run **`rein lens --select tasks`** (which resolves the selection against this plan and writes it into `.rein/plan.yaml`, where the mandate freezes it — after the freeze it reads that list back and never re-derives it, so the library on this machine cannot change what this cycle was reviewed for) and delegate to the `adversarial-reviewer` role (`role-delegation`) in a **fresh context — never the lead that cut the plan** — handing it that lens list, and recording each applied lens with `rein lens --record <id> --found <yes|no> --stage tasks` (`--stage` is what lets `rein lens --grid` place the row) — with `docs/10-requirements.md`, `docs/20-design.md`, `.rein/plan.yaml`, and the `docs/tasks/T-*.md` tickets as its inputs (the lenses attack what `dag --validate/--trace` cannot: duplication and terminology drift between the three documents, acceptance criteria that do not actually satisfy the requirement they cite, vague qualifiers with no measurable criterion, missing `blocked_by` edges, cross-task file collisions, **a ticket whose stated test file or design-mandated ADR path lies outside that task's frozen `scope`**, scope creep, cutover splits). Disposition each finding with one of (`revise_design`, `reduce_scope`, `request_expert`, `dispute_finding: <why>`, …; accepting the risk is not among them) — and **resolve every blocker** before presenting the gate; re-invoke the reviewer once, on the blocker fixes only. Record ticket-affecting outcomes in the ticket's "Notes / design decisions" and the round's summary in the mandate's presentation. A hotfix reduces its *scope* through `/revise`; it does not skip this round. The only way it is skipped is a human switching it off in `.rein/reviews.yaml`, which the chain records with their reason. **Added reviews**: ask every question `rein reviews show --stage tasks` lists of the same inputs, in the same fresh-context launch as the adversarial review — or in one launch of the `adversarial-reviewer` role of its own when that review is OFF — handing each question exactly as printed. Record, disposition and resolve their findings exactly like the adversarial review's, in the round's summary and the affected tickets' notes.
