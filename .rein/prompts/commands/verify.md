# /verify — Test phase

(Phase-scoped rules — gate self-assessment, approval-wait, context budget: read `.rein/prompts/rules/gate-workflow.md` before starting.)
(Capability terms resolve per AGENTS.md "Capability vocabulary" and your agent's capability mapping.)

## Prerequisite check (always first)
Read `.rein/state.yaml` and confirm `gates.mandate == approved` and `gates.acceptance == pending`.
If the mandate is pending there is nothing to verify yet; if acceptance is already approved the
cycle is closed and re-opening it needs `/revise`. **Invoking `/verify` is not itself the acceptance
approval** — this phase assembles the evidence and presents it.

## Steps
0. **Answer any open change requests first.** Run `rein changes list --gate acceptance --json`. Each anchors a place (`docs/...#R-3`, `T-004`, `C-001`) and says what is wrong: **read and edit only the slice it names** — do not re-run the phase over the whole deliverable. Then `rein changes address <id> --note <what you changed>`; the note is what the human reads beside the digests before deciding, so "done" is not an answer. An open request holds the acceptance gate shut, and approving is what closes the addressed ones.
1. Read `docs/test/test-plan.md` and `docs/10-requirements.md` (acceptance points, non-functional requirements). After filling the plan, run `rein dag --trace --test-plan docs/test/test-plan.md` — it mechanically fails (exit 1) any `R-N`/`NFR-N` declared in `docs/10-requirements.md` that never appears in the test plan, so no requirement can silently drop out of verification. Fix the plan until it exits 0 (2 = nothing to check: the test plan is unreadable, or no requirement id exists on either side).
2. **Functional tests**: confirm each requirement's acceptance points are satisfied. Run the automated tests and add any missing verification. Record results in the test-plan table. Also fill the test-plan's **Manual verification checklist** (acceptance automated tests can't cover — real-player/device playback, visual/aesthetic review, supported-OS matrix, long-input/end-to-end performance); mark unrun items and surface them as remaining issues at the acceptance gate.
   - **Deliverable-inventory check (user-facing docs)**: explicitly confirm every existing user-facing deliverable still describes the *current* behaviour — `README*` (all languages/mirrors), CLI `--help`/`--version` text, and any usage docs. A cycle that changes flags/behaviour easily leaves a stale doc behind (e.g. a translated README that was never updated from a prior cycle, or a removed flag still documented). Treat a stale user-facing doc as a defect.
3. **Non-functional requirement tests**: check the criteria checklist (performance, security, reliability/operations). Security is mandatory — record results in the test-plan's security column:
   - **The change's security review is carried here, not re-run.** The acceptance gate already read this cycle's change with the structured security reviewer, and that reading is bound: a blocking finding holds the acceptance gate shut through the same `review_policy.blocking_reasons` the acceptance gate used, this gate's own readiness re-checks the review's `subject_head_sha` against HEAD — so a commit made since the acceptance gate leaves it stale and the acceptance gate does not open — and the receipt binds it by `machine_digest`. Commissioning a second reading here buys the same reviewer's opinion of the same commit, at the price of the largest single read in the workflow, and lands it in a table cell where nothing anchors it. **Record which review this is** — its `subject_head_sha` and the finding counts by severity — so the column points at bound evidence instead of restating it in prose. And a *whole-codebase* read is a different question from "is this change safe", one this cycle never asked: code no task touched is code no gate here approves, and re-reading it every cycle is the largest reading with the weakest tie to what changed.
   - **The dependency audit** — `rein audit run`, which runs the command `security.dependency_audit` names — **on the host, and only there**: an audit reads a published vulnerability database, and no sandbox here is granted egress, so a sandboxed profile is refused rather than left to fail as though the dependencies were what was wrong. A machine that could not answer records nothing at all, and the gate goes on saying no audit has been run. **This is the one that must actually run at the acceptance gate**, because it is the only security answer that is not a function of the tree: the same commit audited last month and today can differ, the vulnerability database having moved while the code did not. That also means it can never be "established" the way tree-bound evidence is, so the record carries the date as well as a digest over this tree's manifests and lockfiles — editing source does not retire it, changing a dependency does, and it expires anyway after `max_age_days`. The acceptance gate's readiness refuses a release with no audit, a stale one, or a failing one; a project that declares no audit command is told it has no dependency answer at all, which is not the same as having a clean one.
   - **A finding here is not this loop's to repair, and that is the routing rule rather than an omission.** A dependency bump changes the closure the gate-③ pinned sandbox image was built from, so it is a change to the frozen environment — which `repair.route` puts in a human's hands, exactly as it does a change to a claim or a requirement.
4. Record discovered defects/vulnerabilities in the test-plan's defect table. A defect in the *code* is not a roll back at all: add the task, and `/build` implements it inside the mandate already approved — no gate moves, because nothing about what was authorized has changed. Only a defect in **what was authorized** — a claim that was wrong, an acceptance criterion that does not mean what it said, a scope that never covered the thing that broke — goes through `/revise --to mandate` at the human's decision, which resets both gates in a chain and re-opens `plan.yaml`.
5. **The acceptance gate**: present **the evidence against the mandate** as an `approval-presentation` — claim by claim, what is established and how, what is `unknown`, and what is still waiting on somebody — then the test result summary (pass/fail, remaining issues, non-functional status), and have the human decide whether to take the change.
   - **Always present a self-assessment as well** (contents: `.rein/prompts/rules/gate-workflow.md` "Gate self-assessment"), centered on release confidence and thinly-verified aspects.

Write the deliverable (`docs/test/test-plan.md`) in the user's language.

## Once approved
- Only after an explicit human "approve": ask the human to run `rein approve acceptance` **themselves** — never for them, and **running the next command is not itself approval** (mechanics: AGENTS.md "Gate rules" 2). Declining is recorded as a change request, not lost — see step 0.
- **Leave a retrospective (recovering the metacognition)**: generate/update `docs/retrospective.md`.
  - Classify needs-revision / blocked into "upstream (requirements/design) defect / implementation convenience / external factor" and summarize the lessons for upstream.
  - **Account for the open items**: `rein events --render` lists every escalation this cycle raised. The log is append-only and has **no `resolve` verb** — a record an operator can close by hand is not evidence of anything — so each escalation is concluded *here*, in the retrospective, together with the fate of any speculative work that was not adopted. Leave none unaccounted for.
  - **Promote durable lessons into the template before `cycle-close` archives the retrospective.** For each item in the retrospective's "Process / template improvement" and "Lessons for upstream" sections, decide with the human whether to lift it into the always-loaded template files (`AGENTS.md`, the procedure files in `.rein/prompts/**`, the per-agent wrappers and capability mappings); apply the agreed promotions and record where each landed (retrospective §5).
- **If `docs/05-current-state.md` exists** (an adopted/ongoing repo), update it with what this cycle changed: new modules, new reusable assets, convention changes, in-flight work that got finished.
- **If the cycle ships as one PR**, offer `rein pr-draft`: it assembles the PR body from the SSOT (gate approvals, task table, requirement coverage, review/coverage digests, commit list) into `.rein/pr-draft.md`. Creating/pushing the PR itself stays outward-facing and human-run — the tool only prints the `gh pr create --body-file` line for the human.
- **If the cycle ships as a stack** (one PR per task, opened as drafts after the build), the acceptance gate is now approved, so offer `rein pr-stack --ready`: it rewrites each body with what the review found and lifts the drafts. It confirms at a terminal first and you never run it for the human — the same rule as `rein approve`. Its output ends by naming `rein pr-stack --merge`, which lands the whole stack in one atomic `gh stack merge` — same rule again: it confirms at a terminal and you never run it for the human. Never offer merging part of a stack: GitHub rebases everything above the cut off the commits the record names.
- Report completion. **To start the next delta cycle** (ongoing repos run Loose Rein as a series of change-scoped cycles), tell the human to run `rein cycle-close --name <slug>` — it archives this cycle's deliverables to `docs/archive/`, restores fresh scaffolds, and resets gates/phase. Closing a cycle is the human's operation, like opening a gate; do not run it yourself. Recommend starting the next cycle in a fresh session: the previous cycle's conversation is no longer needed — its baseline lives in `docs/05-current-state.md` and `docs/archive/` (`.rein/prompts/rules/gate-workflow.md` "Context budget").
