# /tasks — Task breakdown phase

(Phase-scoped rules — gate self-assessment, approval-wait, context budget: read `.rein/prompts/rules/gate-workflow.md` before starting.)
(Capability terms like `structured-question` resolve per AGENTS.md "Capability vocabulary" and your agent's capability mapping.)

## Prerequisite gate check (always first)
Read `.rein/state.yaml` and confirm `gates.design == approved`.
If unapproved, do not work; say "please approve `/design` first" and stop.

## Re-run after a roll back (reconcile, when tasks already exist)
On a re-run after rolling back upstream with `/revise`, if `plan.yaml` already has tasks, **do not rebuild from scratch**. Reconcile the revised design against the existing tasks:
- The `/revise` step normally already marked the impact closure `needs-revision` in code (`rein revise --impacted T-00x,T-00y` — seeds plus transitive dependents). If it did not, mark it now (the read-only enumeration is `rein dag --impacted T-00x,T-00y`).
- Reclassify each marked task: **keep** (unaffected — restore its former status, stating why) / **modify** (needs fixing → stays `needs-revision`) / **obsolete** (no longer needed → mark in notes, do not delete) / **new** (added). "Keep" is a deliberate reclassification presented at gate ③, never a silent default.
- A task that was **`done` but invalidated** reverts to `todo` (needs reimplementation; `/revise`'s mark output lists former statuses). The implemented code stays on the branch but is back in scope plan-wise.
- After reconciling, re-run `rein dag --trace` and confirm the **task thread is reconnected to the revised requirements/design** (no new requirement left uncovered, no dangling reference to a deleted requirement) (confirm exit 0; 1=missing, 2=nothing to check).
- At gate ③, in addition to the usual plan, present the **impact (the impacted list and the keep/modify/obsolete/new classification)** and the **consistency trace** to get re-approval.

On the first run (no tasks generated yet), create them with the steps below.

## Steps
0. **Answer any open change requests first.** Run `rein changes list --gate tasks --json`. Each anchors a place (`docs/...#R-3`, `T-004`, `C-001`) and says what is wrong: **read and edit only the slice it names** — do not re-run the phase over the whole deliverable. Then `rein changes address <id> --note <what you changed>`; the note is what the human reads beside the digests before deciding, so "done" is not an answer. An open request holds gate ③ shut, and approving is what closes the addressed ones.
1. Read `docs/20-design.md`.
   - **Brownfield**: if `docs/05-current-state.md` exists (an adopted repo), **read it first**. Cut tasks to **this cycle's remaining delta** — never create a task that re-implements a capability the baseline already lists as implemented. When the cycle completes an in-flight partial implementation, put an **absorb task** first (kind: foundation): write acceptance-level tests around the existing partial code and pin it green, so the remaining-work tasks stack on a verified base; reference the existing code in the ticket's "Notes / design decisions". **Never create a task as `done`** (a new task is always `todo`) — what already works is baseline description, not a task. If a delta requirement names the combined capability (existing part + remaining work), point the absorb task's `claim_ids` at that requirement's claim and the `rein dag --trace` coverage holds.
2. Split the design into **review-sized task tickets** and create `docs/tasks/T-NNN.md` (following the `T-template.md` scaffold). Each ticket must have:
   - the requirement/design it covers
   - acceptance criteria
   - an **automated-test approach** (kind, **the path of the file the test goes in**, target cases, run command) ← do not create a task without this. `/build` uses it for the green decision.
   - **the paths that answer must be inside this task's `scope`** (step 6): the test file named above, and any `docs/decisions/ADR-*.md` the design section for this requirement says this task records its decision in. A ticket that promises a test and a `scope` that forbids writing it surfaces at `/build` as a `scope_violation`, after an implementer has already done the work. Size the scope here, where it costs a sentence.
3. **Classify each task by kind**:
   - **foundation**: a shared base many tasks depend on (shared models/schema, shared utilities, auth, config, types/interfaces, etc.).
   - **parallel**: feature tasks (leaves) that can run independently and concurrently once the foundation is in place.
   - **integration**: a task that joins several parallel tasks once they complete (integration, E2E, wrap-up).
   - **Cutover decomposition (replacing shared infrastructure)**: when a cycle *replaces* a shared asset that many tasks touch (a colour LUT, an auth layer, a serialization format, a config field), **do not split the removal of the old asset across the foundation/leaf tasks that build the new one**. Deleting the shared old path early makes those intermediate tasks fail their own per-task DoD (`test`+`smoke` can't stay green while producers and consumers straddle two worlds). Instead: keep every intermediate task **additive** (add the new API/field alongside the old, old path still runs at its defaults), and **concentrate the removal of the old infrastructure in the single integration/cutover task** that wires the new path end to end and can delete the old one in the same commit while keeping the suite green.
4. **Assemble the dependency graph (DAG)**: organize each task's `blockedBy` (dependencies) and fan-out (dependents). Confirm there are no cycles (it is a DAG).
5. **Derive the execution plan** from the DAG:
   - **Execution layers**: assign to L0, L1, … in topological order (within a layer, parallel is possible). Foundation should cluster up front.
   - **Critical path**: identify the longest chain (the path that determines the overall duration).
   - **Executable frontier**: todo tasks with no dependencies, ready to start now.
6. **Write the task DAG into `.rein/plan.yaml` (the frozen Expected Model) as the machine-readable SSOT.** The DAG *structure* is frozen at gate ③. Schema per task (`plan.schema.json` is `additionalProperties: false`, so these are the only keys and a stray one fails the write): `id` (unique, `T-NNN`) / `title` / `kind` (`foundation|parallel|integration`) / `blocked_by` (array of task IDs, snake_case, no cycles) / `claim_ids` (the claims this task answers — that, not a `req` string, is what `rein dag --trace` follows back to a requirement) / `domains` / `risk` / `scope` (where this task's work belongs — the loop checks the diff against it; each entry covers the path it names and everything beneath it, and the trailing `/` is optional) / `acceptance` (this task's own bar, below) / `operator_surface` (what this task will require of a *person*, below). **Status is not a task field**: the live value lives in `.rein/state.yaml.tasks` (`todo | in-progress | blocked | needs-revision | awaiting-evidence | done`; newly created = `todo`) and `/build` writes it. There is likewise no per-task `test` command: the DoD is `quality_gate` in `config.yaml`, one definition for every task.

   **`acceptance` is not a second quality gate.** The DoD says the code is *sound*; a task's acceptance criteria say it did *what it was for*, and both run. Each entry is `{id: A-1, statement: <one thing, stated so it could be false>, evidence: {...}}`. `evidence` is optional — most criteria are prose, and saying so is honest — and comes in three kinds: `command` (an argv run in a sandboxed profile, decided by exit status), `artifact` (the named paths must exist), and `external` (evidence this loop cannot obtain: a staging check, a device, a person). A task carrying an `external` criterion reaches **`awaiting-evidence`**, not `done`, until a human records the observation with `rein evidence record`. Putting these in the plan rather than the ticket keeps them out of the implementer's hands: a human freezes this list at gate ③.

   **`operator_surface` is the Expected side of "what does this now require of somebody".** Each entry is `{kind, name, paths, adr?}`: `kind` is one of `persistence` / `public_interface` / `dependency` / `default_value` / `observability` / `security_boundary` (the same words the blind extractor uses, so the two sides compare directly); `name` is what a person deals with, in their words — a settings key, a table and column, a queue, an endpoint; `paths` is where that surface can be *read* at the end, which is both what an extracted statement's code anchor is matched against and what gate ④ offers as the as-built view; `adr` points at where the requirement and its reversibility were decided. Take these from the design's "What this requires of a person / reversibility" lines — do not invent them here. **Declaring nothing is allowed and is not a shortcut**: whatever the code turns out to require of somebody still reaches gate ④, just as something nobody foresaw, at the top of the screen. Example entry: `{id: T-001, title: "define shared schema", kind: foundation, blocked_by: [], claim_ids: [C-001], risk: low}`. The ticket file `docs/tasks/T-NNN.md` is where the human-facing notes live, including which requirement it covers. This is the deterministic truth read by `/build` (the installed `rein build` orchestrator) and `/status` (`rein dag`, which joins `plan.yaml`'s structure with `state.yaml`'s status). fan-out, frontier, layers, and the critical path are derived from `blocked_by`, so they are not stored.
   - After writing, run `rein dag --validate` to confirm no cycles, unknown dependencies, or duplicate IDs (fix if non-zero).
   - **Consistency trace** `rein dag --trace` mechanically checks whether the **requirements → design → tasks thread is unbroken**. The requirement checklist is the `R-N` / `NFR-N` **headings of `docs/10-requirements.md`**, so a requirement nobody wrote a claim for is a break rather than an id the trace never hears about. Exit code **0=whole / 1=broken (fix) / 2=nothing to check (no requirement id on either side — the report says `unknown`, which is not a pass)**.
     - Breaks detected: ① a declared requirement no claim states (ERROR) ② a declared requirement no section of `docs/20-design.md` mentions (ERROR) ③ a claim citing an `R-N`/`NFR-N` the requirements document does not declare — a dangling reference (ERROR) ④ a task with no `claim_ids` (ERROR: it answers for nothing) ⑤ a claim no task is answerable for (WARN). **Non-functional requirements (`NFR-N`) trace with softer rules**: no claim / no design section is a WARN, not an ERROR (cross-cutting NFRs are verified at `/verify`, where `rein dag --trace --test-plan docs/test/test-plan.md` enforces their presence in the test plan) — confirm each NFR WARN is deliberate at the gate.
   - The human-facing task table & execution plan is `rein dag --render` output; present it at the gate (the truth lives in `plan.yaml` + `state.yaml`).
7. **Adversarial review** (required before gate ③): delegate to the `adversarial-reviewer` role (`role-delegation`) in a **fresh context — never the lead that cut the plan** — with `docs/10-requirements.md`, `docs/20-design.md`, `.rein/plan.yaml`, and the `docs/tasks/T-*.md` tickets as its inputs (its gate-③ lenses attack what `dag --validate/--trace` cannot: duplication and terminology drift between the three documents, acceptance criteria that do not actually satisfy the requirement they cite, vague qualifiers with no measurable criterion, missing `blockedBy` edges, cross-task file collisions, **a ticket whose stated test file or design-mandated ADR path lies outside that task's frozen `scope`**, scope creep, cutover splits). Disposition each finding with one of (`revise_design`, `reduce_scope`, `request_expert`, `dispute_finding: <why>`, …; accepting the risk is not among them) — and **resolve every blocker** before presenting the gate; re-invoke the reviewer once, on the blocker fixes only. Record ticket-affecting outcomes in the ticket's "Notes / design decisions" and the round's summary in the gate-③ presentation. A hotfix reduces its *scope* through `/revise`; it does not skip this round (there is no waiver, and no event kind that could record one).
8. **Gate ③**: in addition to the task list, present the **dependency chain (layer diagram, critical path, foundation tasks)**, the **consistency trace**, and the **adversarial-review summary** (finding counts by severity, dispositions, unresolved disputes — the human's to settle) as an **`approval-presentation`** and confirm "may we proceed to implementation with this split and ordering plan?". Generate and present `rein dag --render` (layers/critical-path text, **and how gate ④ will read this plan** — one reading per scoped task, or one reading of the whole cycle when no task declares a `scope`; say which, because a plan read whole is the shape that runs into a session limit and by gate ④ the only remedy left is to split the scope and re-approve) and **`rein dag --trace` (the requirement-coverage table)** — two artefacts, not three: `rein dag --mermaid` draws the same graph `--render` already states (it stays available, and `/status` is where the whole picture is drawn). Make it so the human can see at a glance that **every requirement is linked to a task and there are no dangling references**.
   - **Always present a self-assessment as well** (contents: `.rein/prompts/rules/gate-workflow.md` "Gate self-assessment"), highlighting high-risk tasks (uncertain/external-dependency/coarse-grained); also note low-confidence tasks in the ticket's "Notes / design decisions".

Write the deliverables (`docs/tasks/T-NNN.md`) in the user's language.

## While waiting for approval
`notify-and-wait` first; then only **outcome-independent, throwaway-by-default** work (rules: `.rein/prompts/rules/gate-workflow.md` "While a gate is pending"), recorded as speculative-work events:
- Preparing test fixtures/harness/scaffolding that are clearly needed from the approved design
  (`tests/` is deliberately unguarded for exactly this; code paths in `guard.paths` wait for gate ③).
- **Forbidden**: real implementation of each feature that pre-empts the task plan.

## Once approved
- Only after an explicit human "approve": freeze the plan as gate ③'s deliverable, then ask the human to run `rein approve tasks` **themselves** — never for them, and **running the next command is not itself approval** (mechanics: AGENTS.md "Gate rules" 2). Declining is recorded as a change request, not lost — see step 0.
- **(Only with GitHub integration)** Run `rein issue-sync` to one-way-mirror the approved tasks to Issues. It only acts when `github.enabled: true` in `.rein/config.yaml`, and auto-skips if gh/remote is absent (does not fail). **Do not run it before approval** (avoid making issues for unapproved tasks). `plan.yaml` + `state.yaml` are always the SSOT; Issues are not read back.
- After committing the gate's deliverables, suggest `session-compaction` (pre-compact check: `.rein/prompts/rules/gate-workflow.md` "Context budget") and point to "next is `/build`".
