# /design — Design phase

(Phase-scoped rules — gate self-assessment, approval-wait, context budget: read `.rein/prompts/rules/gate-workflow.md` before starting.)
(Capability terms like `structured-question` resolve per AGENTS.md "Capability vocabulary" and your agent's capability mapping.)

## Where this sits
This writes part of **one mandate**, alongside `/req` and `/tasks`. There is no gate of its own to
wait for and no order to obey: run this before the requirements are finished if the approach is
what the requirements depend on, run it after, or skip it when the change needs no argument about
how. Read `.rein/state.yaml` first anyway — if `gates.mandate == approved`, the mandate is closed
and changing the approach it cites needs `/revise` and a re-approval, so say so and stop.

## Steps
0. **Answer any open change requests first.** Run `rein changes list --gate mandate --json`. Each anchors a place (`docs/...#R-3`, `T-004`, `C-001`) and says what is wrong: **read and edit only the slice it names** — do not re-run the phase over the whole deliverable. Then `rein changes address <id> --note <what you changed>`; the note is what the human reads beside the digests before deciding, so "done" is not an answer. An open request holds the mandate gate shut, and approving is what closes the addressed ones.
1. Read `docs/10-requirements.md` and the existing code/assets.
   - **Brownfield**: if `docs/05-current-state.md` exists, **read it first** — design against its architecture/conventions, reuse the assets in its inventory (state which in the design), and take any existing design docs/ADRs it links as the starting point (the **fast intake** entry described in `/onboard` — the mandate gate approval adopts them).
2. Delegate to the `architect` role (`role-delegation`) — which leaves a `[NEEDS CLARIFICATION: <what>]` marker at every spot it would otherwise have settled on a plausible default — to produce (a) an implementation approach for each requirement, (b) **existing assets that can be reused**, (c) options for important technical choices (with trade-offs across cost/security/non-functional/effort), and (d) for each requirement, **what the approach will require of a person and whether it can be undone** — a setting somebody must supply, a schema somebody must migrate, a dependency somebody must provide, a signal somebody must watch. That is the only place this gets decided: `/tasks` transcribes it into each task's `operator_surface`, reversibility included as a required `reversible` flag, and the acceptance gate shows what the code turned out to require against what was declared here. **The reversibility answer is load-bearing, not annotation**: a task carrying an irreversible surface becomes a contact point of its own, so the loop stops in front of it for a human approval instead of finding out at acceptance that the thing already happened. Say "can be undone by reverting the commit" or name what undoing it would actually take. **If the product is itself an AI agent app**, also have the architect present the agent-specific choices (Architecture pattern / Context strategy / Tool design — the "AI agent application" lens in `.rein/prompts/agents/architect.md`) as options to decide.
3. **Classify every choice by its reach, then present the ones that reach the mandate as options via a `structured-question`.** For each of the architect's choices and `[NEEDS CLARIFICATION]` markers, answer first: *if this is settled wrongly, what does undoing it cost?* A choice whose reversal would move a claim, a scope boundary or what counts as evidence is `reach: mandate` — ask. A choice whose reversal stays inside one task is `reach: local` — settle it yourself and record it in `plan.yaml`'s `decisions` with `settled_by: loop` and a `rationale` for the reach. The criterion is *irreversibility × blast radius*, not "would I otherwise settle this myself"; the second asks about nearly every choice a design contains and spends the drafting phase before the irreversible ones come up. **Within `reach: mandate` there is no cap on how many** — order by **impact × uncertainty** and work down in batched rounds until none is left; the ordering decides what is asked first, never what goes unasked. One round carries about four questions — a property of the capability, not a budget for the phase. A marker ends as a decision recorded in an ADR, as a `local` decision you settled, or as `status: unknown` demoted to `## Open questions` with its assumption spelled out; **demoting is the human's call, not yours**. Create a `docs/decisions/ADR-NNN.md` for each decision a human made. **A decision that changes what somebody has to operate says so in its "Consequences"**: what it requires of a person, and whether it can be undone. Reversibility is a fact about the decision and it is what the acceptance gate's approver is handed later; the pros and cons stay with the options, where the choice actually is.
4. Write the finalized content into `docs/20-design.md`. **Place a design section (`### R-x → design`) covering every requirement (R-x) in `docs/10-requirements.md`, with none missing** — each carrying its "What this requires of a person / Reversibility" line, or an explicit "nothing" where the requirement genuinely asks nothing of anybody. Do not add design with no backing requirement (out-of-scope build-out) on your own — if needed, return it to the requirements side (`/revise`). **If the product is not an AI agent app, delete the scaffold's "AI agent application design" section** (do not leave the conditional block orphaned).
5. **Forward-coverage check**: cross-check that the design **covers all requirements and adds nothing not in the requirements**. Once `docs/20-design.md` has a design section for each requirement, confirm the requirement IDs in the headings match the requirement IDs in the requirements document (this requirement↔design linkage is mechanically re-checked later by `/tasks`'s `rein dag --trace`).
6. **Adversarial review** (required before the mandate gate): run **`rein lens --select design`** (which resolves the selection against this plan and writes it into `.rein/plan.yaml`, where the mandate freezes it — after the freeze it reads that list back and never re-derives it, so the library on this machine cannot change what this cycle was reviewed for) and delegate to the `adversarial-reviewer` role (`role-delegation`) in a **fresh context — never the architect that designed** — handing it that lens list together with `docs/10-requirements.md`, `docs/20-design.md` and `docs/decisions/ADR-*.md`. The `proposed` lenses are the human's call at the gate. Record each applied lens with `rein lens --record <id> --found <yes|no> --stage design` — `--stage` is what lets `rein lens --grid` place the row, and an application recorded without it is counted and shown in every column it could belong to rather than in one. Record every finding in the `## Adversarial review` section of `20-design.md`, each with one of (`revise_design`, `request_expert`, `run_experiment`, `reduce_scope`, `dispute_finding: <why>`, …) — and accepting the risk is not among them. **Every blocker must be resolved** (fixed or disputed-with-reason) before presenting the gate; re-invoke the reviewer once, on the blocker fixes only — no further rounds. Findings that need the human's judgment fold into the gate's single `structured-question` below. A hotfix reduces its *scope* through `/revise`; it does not skip this round (there is no waiver, and no event kind that could record one).
7. **There is no gate here**, and nothing to present for approval: the mandate is presented once the claims have a task DAG answering them (`/tasks`). What this step owes is what that gate will need.
   - **No unresolved `[NEEDS CLARIFICATION]` marker may remain** in `20-design.md` — `rein approve mandate` checks this in code (HTML comments excluded) and refuses while one stands, naming the lines.
   - **No decision with `reach: mandate` may be left `unknown`** — the same check refuses and names them. A design choice nobody can make yet is not made by relabelling it `local`.
   - **Write the self-assessment** into the relevant section of `20-design.md` (contents: `.rein/prompts/rules/gate-workflow.md` "Gate self-assessment"), making low-confidence design spots explicit.
   - **Record the adversarial-review summary**: finding counts by severity, the dispositions, and any unresolved dispute (an unresolved dispute is the human's to settle — never loop further with the reviewer).
   - Tell the human what the design settled and what the mandate still needs. The technical choices were theirs to make (step 3) and they made them; the approval that covers them is the mandate's.

Write the deliverables (`docs/20-design.md`, `docs/decisions/ADR-*.md`) in the user's language.

## While the mandate is unapproved
No product code (`rein guard` denies it), and only **throwaway-by-default** work recorded in `docs/speculative-work.md` (rules: `.rein/prompts/rules/gate-workflow.md` "While a gate is pending"):
- Setting up the skeleton of the dev environment / test harness / CI, lint/static-analysis config —
  **outside `guard.paths`** (e.g. CI config, `tests/`, tooling); a guarded path waits for the
  mandate instead.
- **Read-only investigation** of candidate libraries (install only after finalizing).

Writing the task DAG is **not** speculative work here — it is the rest of the same mandate, and `/tasks` is where it goes.
